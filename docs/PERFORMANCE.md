# 읽기 성능 회귀 기준

2026-09-18. macOS arm64, Qt 6.11.2, Debug 빌드, `offscreen` + 소프트웨어 렌더링. 사용자 PDF나 실제 데스크톱을 조작하지 않고 임시 합성 PDF로 측정했습니다.

## 재현

```sh
QT_QPA_PLATFORM=offscreen QT_QUICK_BACKEND=software build/owelk_ui_tests ReaderPerformance::test_baseline
```

전체 테스트의 한 실행에서 나온 값입니다. 반복 통계나 성능 보장 수치가 아닙니다.

| 항목 | 측정 |
| --- | --- |
| 합성 PDF 페이지 수 | 120 |
| 열기 호출부터 첫 페이지 이미지 Ready·위치 복원 완료까지 | 118 ms |
| 초기 생성 페이지 이미지 항목 수 | 1 |
| 핀치 배율 업데이트 함수 60회 실행 | 78 ms |
| 리더 4개 생성·각 첫 페이지 Ready·복원 완료까지 | 180 ms |
| 4개 리더의 생성 페이지 이미지 항목 수 | 4 |

핀치 60회는 이벤트 루프에 실제 프레임을 60번 표시한 측정이 아닙니다. FPS로 환산하면 안 됩니다. 4개 리더는 같은 합성 PDF를 각각 엽니다. 그림·수식·스캔이 많은 서로 다른 논문보다 가벼운 부하입니다.

테스트는 전체 페이지를 한꺼번에 UI 항목으로 만들지 않는지 검사합니다(단일 리더 12개 미만, 4개 리더 32개 미만). 시간값은 기록만 하고 실패 임계값으로 쓰지 않습니다. 이미지 항목 개수는 메모리 사용량이 아닙니다. RSS·GPU 메모리·실제 프레임 간격은 아직 측정하지 않았습니다.

## 적용한 변경

- 시작 Home에서는 저장된 탭의 실제 PDF 로드를 읽기 진입 시까지 지연합니다. 한 번 읽은 문서를 Home 방문 때마다 언로드하는 방식은 아닙니다.
- 핀치 동안 페이지·선택·링크 좌표의 배율을 연속 변경하면서 기존 래스터 요청 해상도를 유지합니다. 종료 후 최종 해상도를 요청하고 이전 이미지를 유지합니다.
- Document 패널은 활성 리더의 문서 객체를 공유합니다. 썸네일은 가상 목록으로 보이는 범위 주변만 저해상도로 렌더링합니다.

사용한 Qt API: [PdfBookmarkModel](https://doc.qt.io/qt-6/qml-qtquick-pdf-pdfbookmarkmodel.html), [PinchHandler](https://doc.qt.io/qt-6/qml-qtquick-pinchhandler.html), [Image.retainWhileLoading](https://doc.qt.io/qt-6/qml-qtquick-image.html#retainWhileLoading-prop).

## 남은 확인

- macOS 실제 트랙패드에서 핀치 중심점·연속성·최종 선명도, 확대 후 선택·캡처 좌표 확인.
- 대표 논문의 첫 페이지/먼 페이지 이동, 스크롤·선택 지연, 여러 분할의 GPU 프레임·RSS 측정.
- Windows/Linux 빌드와 물리 Ctrl+휠 입력 확인.
- 페이지 수가 줄어드는 일부 탭 전환/닫기 테스트에서 Qt PDF 링크 모델의 `failed to load page` 경고가 남습니다. 이동·닫기 테스트는 통과하지만 이전 페이지 모델의 해제 시점을 추가 점검할 필요가 있습니다.

## 2026-09-20 본문 인덱싱 추가 후

백그라운드 텍스트 추출과 핀치가 PDF 엔진 자원을 경쟁하지 않도록 핀치·문장 선택 중에는 다음 페이지 추출을 기다리게 했습니다. 작업자는 낮은 우선순위를 사용하고 페이지 경계마다 잠시 양보합니다. 대기 중 리더가 닫혀도 작업이 재개되는지 별도로 검사합니다.

추가 단독 실행: 첫 페이지 120ms, 핀치 업데이트 함수 60회 78ms, 4개 리더 192ms, 이미지 항목 수 1/4. `indexingAtPinchStart: true`도 확인했습니다. 위와 같은 합성·offscreen 조건이며 실제 FPS나 큰 논문의 성능 보장값은 아닙니다. Home에서는 리더 로드만 지연하고, 텍스트 인덱서는 별도 작업으로 PDF를 읽을 수 있습니다.

검색 결과로 기존 탭을 재로드하는 테스트에서 빈 소스 전환·기존 페이지 항목 해제에 관한 Qt 경고도 관측됩니다. 해당 테스트는 목적 페이지의 실제 이미지 Ready까지 확인하지만, 실기기에서의 깜박임 여부는 후속 확인이 필요합니다.

## 2026-10-01 출처 지문 캐시·저장 항목 검색

- SHA-256은 파일 스탬프(크기·mtime·ctime·inode)가 바뀔 때만 다시 계산합니다. 이전에는 실행할 때마다 알려진 PDF 전체를 다시 읽었고, 캡처·하이라이트 열기, 리더의 주석 로드(주석이 바뀔 때마다 열린 모든 리더), 검색 결과 이동마다 파일 전체를 읽었습니다. 인쇄는 페이지마다 두 번 읽었습니다. 재실행 시 변경 없는 PDF의 읽기 횟수가 0인지 `PaperIndexTest::restartSkipsUnchangedFilesButReindexesChanges`가 검사합니다.
- 저장 항목 검색(파일명·캡처·노트·하이라이트·워크스페이스)을 작업 스레드로 옮겼습니다. Release 빌드, 논문 2,000·하이라이트 20,000·캡처 5,000개 합성 DB에서 UI 스레드 동기 실행 시 질의당 최대 약 17 ms였습니다. 단발 측정이며 성능 보장값이 아닙니다.
- 출처 확인·폴더 읽기는 저장 작업과 별도 스레드 풀(2개)을 사용해 캡처 저장 중에도 클릭이 대기하지 않습니다.

## 2026-10-05 디자인 개편 후

같은 조건(빌드 형식 동일, offscreen, 실제 사용 데이터 사본, 실행 후 6초·12초의 누적 CPU 시간)으로 개편 전(`ce3e749`)과 비교했습니다.

| | 6초 CPU | 12초 CPU | 메모리(RSS) |
| --- | --- | --- | --- |
| 개편 전 | 2.7–3.7초 | 7.1초 | 189MB |
| 개편 후 | 0.7초 | 0.7초 (가만히 있을 때 0) | 173–174MB |

- 개편 전에는 가만히 있어도 CPU를 계속 썼습니다. 원인은 디자인이 아니라 루프였습니다. ChatGPT 계정(Codex) 정보를 읽으면 제공자 목록이 갱신되고, 항상 만들어져 있던 Settings가 그 갱신을 보고 계정을 다시 읽었습니다. 이제 계정이 실제로 바뀔 때만 갱신하고, Settings는 열린 페이지만 만들며 제공자가 바뀔 때만 계정을 읽습니다(`tst_settings`의 `test_aiPageAsksForTheAccountOnce`).
- 메모리 약 15MB 감소: Canvas 아이콘(창 하나에 25–30개와 목록 행마다) 대신 글꼴 아이콘, 열려 있을 때만 만드는 Settings.
- 새 PDF 하나를 연 빈 데이터에서는 두 버전 모두 가만히 있을 때 CPU 0, 메모리 173–175MB입니다.
- 테마·강조색·글자 크기 변경은 바인딩을 한 번 다시 계산할 뿐 프레임마다 하는 일은 없습니다. Dark pages 셰이더는 켰을 때만 페이지 이미지에 붙습니다.
